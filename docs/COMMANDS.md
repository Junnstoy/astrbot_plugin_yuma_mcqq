# 自定义指令、清洗与模板

本文对应 1.4.0，配置 schema 为 4。

每条自定义指令是独立 action，而不是共享一个正则入口。GUI 创建配置后即注册到 AstrBot 的管理行为；稳定 `id` 用于注册和操作去重。修改实际触发名、别名和入口启停请使用 AstrBot 管理行为，GUI 显示这些生效值。配置中的 `name/aliases` 是注册初始值；已有管理行为覆盖优先。

## 唤醒前缀与内置查询

`command_prefix` 默认为空，沿用 AstrBot 的唤醒规则。填写 `mc` 后，`mc签到` 和 `mc 签到` 都能触发本插件，也继续遵守管理行为中的实际命令名称、启停与管理员权限。该前缀不修改其他插件的命令规则，不作为普通聊天转发到游戏。全局 `points_name` 只修改货币显示，默认“点数”；默认动作名称不随货币改名，需改触发名时使用管理行为。

1.4.0 内置动作共 23 个。查询与历史图片分开：

| 默认命令 | 行为 |
| --- | --- |
| `服务器状态` | 仅回复 `在线` 或 `离线`，依据当前路由的 QueQiao 连接状态 |
| `tps` | 执行服务器 `tps_command`，默认 `tps`，返回实际清洗后的文本 |
| `mspt` | 执行 `mspt_command`，默认 `mspt`，返回实际清洗后的文本 |
| `ping` | 执行 `ping_command`，默认 `ping`，返回实际清洗后的文本 |
| `性能图 [小时数]` | 历史 PNG；默认 24 小时、范围 1–168；没有历史时尝试采样 |

前三个性能文本查询与状态查询不接受时间范围参数。请根据服务端实际安装的插件调整查询命令；收到错误文字时不会伪造指标。普通 `ping` 可能只返回 `Pong!` 或不能在控制台执行，QQ 仍收到实际回包经清洗后的原文；自动采样无法提取毫秒数时记录缺失值，GUI 和 PNG 显示缺失，不写成 0。自动采样及 GUI 曲线独立运行，玩家 ping 与机器人到服务器 RTT 分开标记。

启动读取旧配置 v2 时，精确等于 `spark tps` / `spark ping` 的旧默认查询会一次性改为 `tps` / `ping`，其他自定义值不变。该迁移完成后主动重新选择 Spark 命令也会保留；当前配置会继续升级到 v4，详见 [配置迁移约定](IMPLEMENTATION_CONTRACT.md#配置-v3)。

## 帮助展示

“指令与帮助 → 帮助展示与说明”统一列出默认与自定义命令，显示管理行为的实际名称。可编辑说明、设置帮助显隐、调整排序数字或上移/下移。“帮助回复设置”可切换图片和文字；默认图片开启，`mc帮助` 只发送一张深色图片，每列最多 15 条命令，超出自动新增一列，不分页。分类标题不计入 15 条上限。

图片和文字都遵守全局帮助顺序。图片逐列从上到下、从左到右排列，每条命令保留全局编号；仅将连续的同类内容框在同一个矩形内，同类跨列或中间插入其他分类后使用“续”标题。帮助命令默认排第一，用户已有的显式排序优先，调整自定义命令位置也会按顺序体现在图中。

帮助内容超过渲染尺寸上限、缺少中文字体或图片生成失败时，返回同份完整文字；不省略后面的命令，也不拆成多张图片。查看[单图帮助样张](screenshots/help-example.png)。GUI 中帮助编辑表的分页只影响管理列表，不决定群内帮助图片的数量。

帮助显示设置不启用指令或改变权限。停用、隐藏、当前用户无权使用的动作不会出现在群帮助中，图片和文字遵守相同规则。默认说明留空可恢复；用户编辑的说明不会被命令改名时自动替换。

持久配置为 `help.image_enabled` 及 `help.entries`。内置键如 `signin`，自定义键如 `custom:list`（使用稳定配置 ID）；每项支持 `description`、`visible`、`order`，未指定排序沿用默认分组顺序。1.4.0 沿用这些配置，无需迁移或重填。具体入口见 [1.3 更新说明](UPGRADE_1_3.md)，单图行为见 [1.4.0 更新说明](UPGRADE_1_4.md)。

## 管理员原样 RCON：cmd

`cmd` 仅供管理员使用，无需绑定 MC 账号。它把后面的正文作为一条 RCON 命令，发送到当前群 UMO 路由配置的服务器，并把实际回包经通用清洗后的文本回复到原 UMO。例如：

```text
cmd cmi ping rincho
```

也支持包含 JSON 的命令；引号、花括号和 JSON 内容按字面量传递，不进行自定义模板插值。例如下面的 `{player}` 就是要显示的文字，不会替换为绑定玩家名：

```text
cmd tellraw @a {"text":"{player}","color":"gold"}
```

实际触发名可在 AstrBot 管理行为中修改，并遵守插件唤醒前缀。命令仍受传输层单条命令长度及控制字符检查约束。同一 UMO、消息 ID 和动作的重复投递不重复发送；发送后超时、断连或无法确认的结果保留为未知，不自动重试。重新发送一条新消息属于新请求，涉及发奖等副作用时应先核对上次结果。

## 绑定与管理员操作

以下是默认触发名；改名后以 AstrBot 管理行为为准，唤醒前缀仍按上文配置生效。

| 默认命令 | 目标与权限 |
| --- | --- |
| `绑定 MC名` | 为自己绑定；普通用户按配置选择直办或验证码验证 |
| `修改绑定 MC名` | 修改自己的绑定；普通用户遵守验证模式和冷却 |
| `解绑` | 解除自己的绑定；普通用户遵守冷却 |
| `绑定 QQ号 MC名` | 管理员为指定 QQ 绑定 |
| `修改绑定 QQ号 MC名` | 管理员修改指定 QQ 的绑定 |
| `解绑 QQ号` | 管理员解除指定 QQ 的绑定，或取消其待验证绑定 |

管理员为自己操作也走管理路径：上述绑定、修改和解绑均免本次 CD 检查，开启验证码模式时仍直接办理，无需游戏验证码。GUI 的管理员解绑调用同一路径。管理员不能占用其他 QQ 已绑定的 MC 身份；已有其他绑定时仍应使用“修改绑定”。管理操作会作废目标 QQ 的旧验证码，并保留或更新后续普通用户操作的冷却，不清除点数、签到和绑定历史。操作人和目标 QQ 写入审计。

管理员输入单个纯数字参数，如 `绑定 QQ号`，按缺少 MC 名返回用法；管理员绑定纯数字玩家名时使用 `绑定 自己QQ 数字MC名`。普通成员的 `绑定 12345` 仍表示绑定自己的纯数字 MC 名，两个参数的代操作语法仅限管理员。

## 自定义模板指令处理链

```mermaid
flowchart LR
  A[唤醒和名称命中] --> B[管理员 / 绑定 / 冷却]
  B --> C[按类型校验参数]
  C --> D[渲染一条RCON命令]
  D --> E[保存操作ID后发送]
  E --> F[共用清洗器]
  F --> G[当前指令解析器]
  G --> H[状态与命名字段]
  H --> I[当前状态的回复模板]
  I --> J[原始UMO]
```

清洗器去除 ANSI、Minecraft `§`/`&` 传统及十六进制颜色、控制字符、示例中的时间戳与 `Rcon:` 前缀，以及配置中显式给出的插件前缀。不会删除任意方括号内容，以免误删实际业务文本。

解析方式：`rules` 为完整正则匹配，`litesignin` 为已给定签到回包，`text` 为只清洗查询结果。`text` 的 `SUCCESS` 仅表示收到了文本，不能用来证明发奖或扣费已完成。多条规则同时匹配、超时、玩家不一致、空/未知回包均进入 `UNKNOWN`。

正则使用命名捕获 `(?P<player>...)` 等字段。每次匹配限时 50ms、输入限长；不要使用不完整的关键词“成功”判断关键操作。命令参数支持 `word`、`integer`（上下限）、`player`、`enum`（choices）。不支持任意 Python、属性访问或多条命令拼接。

模板只支持 `{字段名}`，花括号原文使用 `{{` 和 `}}`；不支持 `{obj.attr}`、`{x[0]}` 或格式转换。命令缺少参数会被拒绝，显示模板中不存在的字段为空。回复常用字段为 `player`、`player_name`、`user_id`、`date`、`points_name`、`cleaned`、`rcon`、`status` 和当前规则命名捕获。`cleaned` 是去掉该命令配置前缀后的识别文本；`rcon` 是仅经通用清洗的完整回包，保留插件前缀。RCON 命令本身只接受基础身份字段、日期及显式声明的参数，不等于回复模板的所有字段都可作为命令参数。

## 只读查询示例

可在 GUI 按字段填写以下配置；这条动作允许无需绑定的成员查询在线名单：

```json
{
  "id": "online_list",
  "name": "在线玩家",
  "aliases": ["在线名单"],
  "enabled": true,
  "admin_only": false,
  "require_binding": false,
  "cooldown_seconds": 5,
  "server_id": "",
  "rcon": "list",
  "parameters": [],
  "parser": "text",
  "cleanup_prefixes": [],
  "rules": [],
  "templates": {"SUCCESS": "在线信息：\n{cleaned}", "UNKNOWN": "结果未识别，请联系管理员。"}
}
```

`server_id` 留空跟随当前路由；需要绑定的动作还会验证绑定服务器与目标一致。管理员创建的 RCON 模板按控制台权限运行，所以默认 `admin_only: true`；仅将明确允许成员使用的动作开放。

## LiteSignIn 签到

内置“签到”使用专门的两阶段业务，不应替换成只执行 RCON 的自定义命令。默认解析以下两条清洗后的结果：

```text
成功给玩家 rincho 签到， 当前该玩家已连续签到 1 天。
玩家 rincho 今天已经签到了，请不要重复签到。
```

第一条得到 `SIGNED` 和 `player/days`，第二条得到 `ALREADY_SIGNED` 和 `player`。两者都进入群签到判断；游戏已经签到不代表群也已签到。

| 路由字段 | 作用与默认值 |
| --- | --- |
| `signin_command` | 实际游戏命令，默认 `signin click {player}` |
| `signin_prefixes` | 仅在匹配前移除列出的文本前缀，默认 `["[手记人偶]"]`；颜色自动清洗，不用填写颜色码 |
| `signin_rules` | 默认 `[]` 沿用内置规则；只有服务端回包措辞变化时才需自定义 |
| `templates.signin` | 首次群签到成功回复，含游戏本次成功或游戏已签到两种情况 |
| `templates.signin_already` | 游戏确认后，群内今日已签到的回复 |

自定义规则只接受 `SIGNED/ALREADY_SIGNED/FAILED`；成功或重复状态必须有命名捕获 `player` 用于核对。默认规则也使用自定义 `signin_prefixes`。这些前缀不会从展示变量 `{rcon}` 中删除。

群成功与群重复默认都使用同一份三行结构，分别展示玩家、群结果与本次游戏结果：

```text
玩家: {player}
{group_result}
{game_result}
```

| 本次游戏回包 | 群今日尚未签到 | 群今日已签到 |
| --- | --- | --- |
| `SIGNED` | 群成功 + 游戏成功 | 群重复 + 游戏成功 |
| `ALREADY_SIGNED` | 群成功 + 游戏重复 | 群重复 + 游戏重复 |

两个结果变量的完整文案为：

```text
群内签到成功✅️ 本次获得: {points_delta} {points_name} 当前{points_name}:{balance}
群内签到失败❌️ 今日已签到 请不要重复签到
游戏签到成功✅️ 已连续签到 {days} 天。
游戏签到失败❌️ 今日已签到 请不要重复签到
```

每条通过每日时段检查的新请求仍先执行游戏签到；时段外不会发送游戏命令。群重复不会覆盖本次游戏成功或连续天数。游戏重复回包没有天数时，`days` 为空；旧已存结果或自定义成功规则缺失天数时，默认游戏行只显示“游戏签到成功✅️”。真实失败、未知回包和跨日请求返回各自原因，不使用重复签到文案。`{rcon}` 仍可在自定义模板中展示完整清洗回包，其他变量见 [业务规则](BUSINESS.md#两阶段签到)。

在“连接与群服 → 签到时段与活动”配置每日允许时段、日期范围活动。倍率活动按原奖励范围抽样后乘倍率并向下取整；范围活动替换抽样上下限。同日只应用优先级最高的活动，不叠加；同优先级、同日期重叠的启用活动不能保存。日期和时间均按路由时区，共享点数作用域的路由统一策略。该页提供不发 RCON、不写账的策略预览，详见 [1.4 使用说明](UPGRADE_1_4.md#签到时段与活动)。

GUI 将 `signin` 与 `signin_already` 作为独立文本框，清空覆盖后恢复默认。升级配置到 v4 时，只移除精确等于旧官方默认文案的这两项覆盖；其他自定义回复保留，详见 [配置迁移约定](IMPLEMENTATION_CONTRACT.md#配置-v3)。

GUI 的“签到回包解析示例”是两阶段纯预览：粘贴回包、填写期望玩家，选择路由以使用其规则和模板，模拟“群今日已签到”、奖励及最终余额，即可查看四种组合。未知或错误玩家回包不产生模拟奖励。它不读取真实账户、不写数据库、不连接 RCON；通用指令的“模拟回复（不执行）”也只处理样本文本。诊断页的“执行 RCON”才会真正发送命令。调整规则时先分别试成功、重复、失败、错误玩家及陌生回包，再保存并在实服验收。

## 转发类型与游戏事件

`route.types` 控制 QQ → MC 的消息组成：文本、表情、@、图片、链接、语音、视频、文件、合并消息、引用分别可开关；`route.events` 控制 MC → QQ 的聊天、加入、退出、死亡和成就事件。GUI 使用两组复选框，方向总开关 `qq_to_mc` / `mc_to_qq` 在其上生效。它们不控制业务命令解析。

QQ → MC 的 `prefix` 默认 `[{group}] {sender}{reply}：`，可写 `{group}`、`{sender}`、`{user_id}`、`{reply}` 并使用支持的 Minecraft 颜色代码。`{reply}` 将引用标记放在指定位置，无引用时为空；自定义前缀不含该变量时，引用仍作为消息正文组件展示。配置 v4 仅将精确等于旧官方默认 `[{group}] {sender}：` 的前缀升级，其他自定义前缀保留。

引用悬浮使用 `templates.reply_hover`，支持引用发送者 `{sender}`、消息摘要 `{message}` 和时间 `{time}`，默认三行：

```text
{sender}
{message}
Date: {time}
```

路由 `message_colors` 可分别设置九类消息组件的颜色：

| 类别 | 字段 | 默认颜色 |
| --- | --- | --- |
| 链接、图片、语音、视频、文件、合并消息 | `link`、`image`、`record`、`video`、`file`、`forward` | `blue` |
| 引用 | `reply` | `gray` |
| QQ 表情 | `face` | `green` |
| @ 提及 | `at` | `yellow` |

颜色支持 `#RRGGBB` 或 Minecraft 的 16 个名称：`black`、`dark_blue`、`dark_green`、`dark_aqua`、`dark_red`、`dark_purple`、`gold`、`gray`、`dark_gray`、`blue`、`green`、`aqua`、`red`、`light_purple`、`yellow`、`white`。这是组件展示颜色，与 RCON 回包清洗和消息类型开关分别配置。

MC → QQ 的 `templates.mc_to_qq` 默认 `[{server}] {message}`，其中 `{server}` 使用服务器 `display_name`，留空时回退到鉴权 `name`；`{server_name}` 始终是鉴权名称。真实 QueQiao `name` 不应为了改显示文字而改动。

未知自定义命令结果保存在操作记录，相同 UMO/消息 ID/action 不重发。**重新发送一条新消息是新请求**，因此涉及不可重复副作用的操作应设计服务器侧幂等或使用商店订单流，并先核对已有结果。
