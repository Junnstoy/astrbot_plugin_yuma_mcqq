# 旧点数数据迁移

旧插件只作为数据来源。新插件不加载旧插件 Python 代码，不继承旧唤醒头、命令、签到策略、倍率、重置和补签流程，也不会自动发现或导入生产数据。

迁移入口位于已登录的 AstrBot 插件管理 GUI，调用 `import_preview` 和 `import_apply`。只支持旧 `astrbot_plugin_checkin_points` 的 SQLite 数据布局；读取时使用只读连接。单个文件上限为 256 MiB，单表最多 100000 行，超过限制会停止导入，需要离线处理。

## 迁移前准备

1. 暂停旧插件的签到、调整点数和商店交付，等待执行中的任务结束。不要让新旧插件同时操作同一套业务。
2. 制作旧数据库的一致性副本。停止旧进程、确认数据库连接已关闭后复制文件，或使用 SQLite 官方 backup API 制作副本。存在活跃写入时，不能只复制主 `.sqlite` 文件而遗漏 WAL 中的数据。
3. 暂停新插件的点数相关操作，为新插件整个数据目录制作一致性备份。`domain.sqlite3` 保存余额、流水、订单、绑定及迁移记录；`settings.json` 保存新配置。备份应保留原始快照，放在插件服务不会公开分发的目录。
4. 在新 GUI 配置 QQ 会话 UMO、Paper/QueQiao 连接及点数 `scope`。默认一个 UMO 对应一个独立点数作用域；确需多个群共用点数时，明确配置同一 `scope`。

这些准备由管理员显式完成。迁移接口本身不复制数据库，也不停止旧插件。

## 预览、映射和确认

`import_preview` 的载荷：

```json
{"path":"D:/offline-backup/legacy-points.sqlite"}
```

预览返回各表记录数、旧作用域余额总和、注意事项、`already_imported` 和 `digest`，不返回兑换码或私聊奖励。`digest` 是所支持表的内容摘要，不是数据库文件字节摘要。预览不修改新库。

核对预览后，通过 `import_apply` 提交完全相同的路径和摘要，并明确确认：

```json
{
  "path":"D:/offline-backup/legacy-points.sqlite",
  "digest":"预览返回的完整摘要",
  "confirmed":true,
  "scope_map":{"旧session值":"新配置的点数scope"}
}
```

`scope_map` 是旧 `session` 到新 `scope` 的 JSON 对象；未配置的旧作用域保留原值。预览的余额汇总仍按旧作用域显示。映射影响余额、签到、商品、兑换码和订单；原始记录另行完整归档。订单不会因为映射而主动向任何群发消息，用户在对应新作用域主动补领时才交付。

执行时会重新读取副本并比较 `digest`。内容变化则必须重新预览。所有导入写入使用一个 SQLite 事务，校验或插入失败会整体回滚。同摘要只能成功导入一次；重复请求返回 `already_imported: true`，不会再增加余额。已经导入的摘要不能通过改变映射再次导入。

目标中存在相同作用域、相同 QQ 的账户时会拒绝导入，即使该账户余额为零。商品编号或签到日期冲突也会拒绝，不会覆盖或悄悄相加。请使用空目标或明确的新作用域，避免把多个有交集的旧作用域映射到同一目标。

## 数据对应关系

| 旧数据 | 新数据处理 |
| --- | --- |
| `balances` | 当前余额作为迁移期初值入账，生成一次 `migration_opening` 流水；不重新累计旧签到或旧审计中的变动 |
| `checkins` | 已入账记录迁入签到历史，保留用户、作用域、日期与原点数；同日再次群签到不会重复发点。旧版本没有 `credited` 字段时视为已入账 |
| `session_settings.products` | 文本和兑换码商品迁入，全部默认为下架；管理员核对新规则、价格、奖励和库存后显式启用 |
| 商品兑换码库存 | 迁入原库存；相同作用域/商品/码内容去重 |
| `used_codes` | 永久标记已使用，即便旧配置还把同一码放在库存里也不会再次销售；重新导入同一码不会恢复库存 |
| `purchases` | 保留订单快照、接收人、价格和原奖励；转换状态见下表 |
| 只有名字的 `bindings` | 只归档，不建立有效绑定；用户重新绑定时按当前开关直接绑定玩家名，或通过游戏验证码验证真实 UUID，不伪造 UUID |
| `balance_audit`、`checkin_resets`、其他旧配置 | 只归档，不自动执行对应业务，也不再次影响余额 |

上述支持表的原始记录均保存在新库 `legacy_records`，包括未入账签到和原绑定；`migration_batches` 记录摘要和管理员。归档可能含兑换码及奖励，仅用于管理员离线审计，不通过公开状态、群回复或媒体服务输出。未识别的其他表不导入。

## 旧订单与补领

| 原订单状态 | 导入后的状态与行为 |
| --- | --- |
| `delivered` | `fulfilled`；保留已交付记录，可补领同一份私聊文本/兑换码，不再扣点 |
| `paid`、`sending`、`delivery_failed` | `paid_pending`；原系统已经扣过款，主动补领保留的同一份奖励，取得 OneBot 消息 ID 后完成，不再次扣点 |
| `pending`、`cancelled`、`expired` 及其他未识别状态 | `cancelled`；不自动继续旧未付款订单 |

迁移不会触发私聊、RCON 或批量补发。旧 `sending` 可能实际上已发送，所以只允许补领同一份原奖励，不重新分配兑换码。`paid_pending` 的失败补领仍回到待补领，进程重启也不会自动发送。

已付款的迁移订单不能直接自动退款。如果确认需要退款，管理员先核对旧账本，再显式调整点数并填写依据。不要用再次导入或重建奖励来补偿未知交付。

## 验证与回滚

导入后先核对各作用域总余额、抽查用户余额和签到日期、检查已用码数量与待补领订单，再启用新业务。旧商品默认下架，旧绑定必须重新建立；默认可直接按玩家名绑定，启用 `binding_verification_enabled` 后才需要游戏内验证。

这与本插件自身的数据库版本升级不同：本插件早期保存的真实 UUID 绑定会自动事务升级为带 `identity`、`verified` 字段的结构，保留 UUID、历史和冷却。该升级不扫描或导入其他插件的数据。如果早期数据存在不同 QQ 绑定同一玩家名的冲突，升级会回滚并给出错误，应保留备份、解除冲突后再升级。

需要回滚时，先停止新插件并等待所有处理任务结束，保存当前数据库用于交付核对，再恢复导入前的一致性备份。不要运行中覆盖 SQLite 主库或手工删除 WAL。数据库回滚不能撤回已发送私聊、已执行游戏命令和已兑换奖励：回滚前后都应记录这些外部交付，恢复后先核对未知订单，不自动重发。仅恢复旧插件也需要遵守这一点。
