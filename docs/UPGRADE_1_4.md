# 1.4 系列升级说明

当前版本为 1.4.1。1.4.0 增加每日签到时段、日期奖励活动，并将 `mc帮助` 改为一张自动分栏的分类图片；1.4.1 调整点数排行并优化转发查询。配置 schema 仍为 4；保留现有数据目录并备份配置、数据库后更新插件、重载。已有绑定、余额、签到历史和帮助说明继续使用，不需要重新导入旧库。

## 1.4.1 补丁（2026-11-01）

`点数排行` 固定显示当前点数作用域总余额前 10 名，使用当前绑定的 MC 玩家名。换绑后显示新名；未绑定或已经解绑的账户显示“未绑定玩家”，不回退显示 QQ 号或历史玩家名。总余额包含冻结点数，排序口径与同分次序保持原有规则；不足 10 个账户时显示全部，空榜仍显示“暂无记录”。此修改不改动账户和绑定数据。

图片转发的 `[图片]` 标签出现慢，与点击后图片加载慢是不同阶段。原有的公开 HTTP(S) 媒体地址直接作为点击链接，插件本来就不需要下载它；没有公开地址时才查询 NapCat 或发布可用的缓存资源。此次排查针对转发前的消息信息合并和必要查询，不能据隔离测试认定实服延迟已彻底消失。后续仍应结合转发日志确认具体阶段。

另已核对官方 AstrBot 4.29.1 的预处理代码：正文和引用中的图片会逐张转换为本地文件，远程图片可能在进入本插件前就被下载。这一步不以是否唤醒 AI 或是否开启图片理解为条件，修改本插件优先级也不能绕过。下方 `framework_wait` 用于估算这类前置等待，但不能单凭一个总时长认定具体原因。

1.4.1 保留原始消息与框架消息对应媒体段中已有的可用 URL，避免文件 ID 或空字段覆盖它，也识别 `file_path` 中的 HTTP(S) 地址。当前层媒体来源和引用元信息最多 4 个并行查询，实际显示顺序不变；取消请求会清理未完成的查询。没有公开链接的单张图片仍可能等待 NapCat 查询，缓存发布和来源校验规则保持不变。

### 转发耗时排查

重载 1.4.1 后，在同一个测试群依次发送普通文字、单张图片、多张图片、带引用的图片，记录 QQ 发送到游戏标签出现的大致间隔；同时在 AstrBot 日志中搜索 `QQ-to-MC slow`。点击链接后才开始的图片加载耗时不属于标签转发阶段。

慢阶段达到 1 秒会记录 WARNING，同一阶段每 30 秒最多记录一条，格式为：

```text
[YumaMCQQ] QQ-to-MC slow stage=onebot.get_image elapsed=1.250s
```

| 阶段 | 核对方向 |
| --- | --- |
| `framework_wait` | 从 AstrBot 事件创建到本插件入口的估计等待，包含队列、框架预处理和前序处理器，不包含 NapCat/平台适配阶段 |
| `onebot.get_image` | NapCat 查询图片地址的耗时；已有公网地址时通常不需要此查询 |
| `onebot.get_msg` | 获取引用消息的耗时 |
| `onebot.get_record` / `onebot.get_file` | 语音或其他附件来源查询 |
| `onebot.get_group_file_url` / `onebot.get_private_file_url` | 群文件或私聊文件链接查询 |
| `onebot.get_forward_msg` | 合并消息内容查询 |
| `media_cache` | 需要发布缓存资源时的处理耗时 |
| `relay_queue` | 等待插件转发并发槽的耗时 |
| `render` | 消息组件准备的总耗时，可能包含查询和缓存；不要与这些子阶段相加 |
| `queqiao_broadcast` | 插件向 QueQiao 广播阶段的耗时 |

先看 `framework_wait` 与插件内各阶段的差别，再比较 `onebot.*`、`media_cache`、`queqiao_broadcast` 及插件排队时间。`framework_wait` 以事件的 `created_at` 和系统当前时间估算，受系统时钟调整影响，不等于 QQ 网络延迟；框架没有有效创建时间时不记录这一项。其余阶段使用本插件内计时。

如果主要等待出现在 `framework_wait`，在 AstrBot 当前群生效配置的“群聊上下文感知”中核对“群聊消息记录注入上下文”“自动理解图片”和“群聊图片转述模型”。当记录注入、自动理解均启用且配置了群聊图片转述模型时，普通非命令图片可能先逐张等待模型转述，之后才到本插件。对应配置是 `provider_ltm_settings.group_icl_enable`、`provider_ltm_settings.image_caption`、`provider_ltm_settings.image_caption_provider_id`；这里的群聊图片模型与 `default_image_caption_provider_id` 分开。

需要对照时，可在该群暂时关闭“自动理解图片”，再发送同样的测试图片比较耗时。关闭只避免这条群聊图片转述路径的模型等待，**不会关闭框架预处理中的远程图片下载**。本插件没有修改 AstrBot 预处理、处理器优先级或你的模型配置。

日志只记录阶段和时长，不含消息正文、QQ、UMO、文件 ID 或资源链接。两轮对比留出 30 秒以上，避免同阶段限频影响观察。没有慢日志不能证明上游没有延迟；平台适配前的等待也不在 `framework_wait` 范围内。生产环境的具体慢点仍需以实际日志核对。

## 签到时段与活动

打开“连接与群服”，在目标路由行选择“签到时段与活动”。每日时段默认关闭，活动列表默认空；更新后不会自行改变发奖规则。

每日时段限制整条签到指令。开启后，在允许时段之外不发送 `signin click 玩家`，也不新建签到结算记录。时间按该路由的签到时区解释，默认 `Asia/Shanghai`：

- `08:00–23:00` 包含 08:00 和 23:00 这两分钟，直到 23:00:59。
- `22:00–02:00` 表示跨午夜时段，包含每天 22:00 到次日 02:00:59；签到日期仍是当地自然日，不把凌晨归到前一天。
- 起止时间相等仅允许那一分钟；需要全天可签时关闭时段限制，或设为 `00:00–23:59`。

奖励活动填写名称、开始/结束日期、模式、参数、优先级和启停状态。起止日期都包含在内；没有命中活动时使用路由原本的奖励上下限。

| 模式 | 计算方式 | 示例 |
| --- | --- | --- |
| 点数倍率 | 先在原奖励上下限内抽取整数，再乘倍率并向下取整 | 基础抽到 3，倍率 1.5，最终 4 |
| 奖励范围 | 使用活动上下限替换原抽样范围，不叠加倍率 | 活动设为 20–30，则本次在 20–30 内抽取整数 |

同一天命中多个活动时只使用优先级最高的一项，不叠加。启用中的活动若日期重叠且优先级相同，保存会拒绝并提示调整。倍率允许 1–1000、最多 6 位小数；奖励上下限允许 0–1,000,000，最终单次奖励不超过 1,000,000,000。

多个路由共享同一个点数作用域时，也共享每日时段和活动。该入口保存时会同步到同作用域路由；路由时区和基础奖励仍需保持一致。它不会修改群转发、管理员、游戏命令或其他业务配置。

“预览”可选择一个当地日期时间，并可填写模拟抽样点数，查看时段是否允许、命中的活动及预计奖励。预览不读取真实账户、不执行 RCON、不写账。时段外展示的奖励范围仅供核对规则，不表示当时可以签到；回包文字的四种组合仍在诊断页“签到回包解析示例”预览。

新请求通过时段检查后仍先游戏签到，再结算群签到。抽样结果、活动和最终奖励会随操作保存，同一消息重试不会重新抽奖；已确认游戏成功的操作恢复时只完成本地结算，已完成结果可以重放，未知游戏结果不自动重发。调整活动不会追溯修改旧账本，也不会重置当日群签到次数。

## 单张帮助图片

“指令与帮助 → 帮助展示与说明 → 帮助回复设置”保留图片开关。开启时只返回一张深色分类图；关闭时返回完整文字。帮助继续采用 AstrBot 管理行为实际名称、别名和权限，默认与自定义指令的说明、显隐、排序均沿用。

图片严格按全局帮助顺序逐列排布，从上到下、从左到右。每列最多 15 条命令，分类标题不计数；超过 15 条自动新列，最少一列，普通字号保持不变。连续的同类内容使用矩形框，同类跨列或被其他分类打断后使用“续”标题；每条命令保留全局编号。

帮助命令默认排第一，已保存的显式排序覆盖仍优先。调整默认或自定义指令的位置会同时影响图片和文字；分类框不会把已插入的自定义命令移回分类末尾。

实际输出依当前配置和权限生成。超过渲染尺寸上限、缺少中文字体或图片生成失败时，回退同份完整文字，不截断命令、不拆成多张图片。中文字体要求沿用 [1.3 部署说明](UPGRADE_1_3.md#帮助图片说明显隐与顺序)，插件不联网下载字体。

GUI 数据列表分页、引用标签与颜色、服务器 ID 修改和性能图规则继续有效。测试证据与尚未执行的实服验收见 [验证记录](VALIDATION.md)。
